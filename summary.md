# Summary of the 1:Many Model for Digital Twins

## Introduction
Pheromone is a distributed digital-twin platform that implements a 1:Many model for managing server topology and workloads. The model combines OS-level twins and workload-level twins to provide comprehensive mapping of infrastructure, enabling autonomous resource management, performance optimization, and real-time observability across distributed nodes.

**Agents in Pheromone are agentic AI-capable agents** (see [ADR-007](docs/adr/adr-007-agentic-ai-agent-model.md)). Each agent runs an autonomous AI reasoning loop on the instance it manages. Digital twin management is a core *skill* of the agent: the agent reads, updates, and applies its twin model to the system under management, embodying the pheromone metaphor of decentralised, intent-driven communication.

The platform is implemented primarily in **Go 1.24+** and communicates over **gRPC / Protocol Buffers** (see [ADR-003](docs/adr/adr-003-grpc-contracts.md)). Twin state is persisted in a hybrid in-memory + etcd store (see [ADR-002](docs/adr/adr-002-server-architecture.md)) and events flow through a NATS JetStream message bus (see [ADR-005](docs/adr/adr-005-message-queue.md)).

## Key Architectural Layers
1. **Infrastructure Layer**  
   Represents the physical hardware and foundational software elements that manage resources.

2. **Platform Layer**  
   Includes the OS-level twins that abstract the underlying infrastructure, providing a virtualization layer to interact with the hardware. Twin schema is defined in [ADR-004](docs/adr/adr-004-twin-model-schema.md).

3. **Application Layer**  
   Contains workload-level twins, representing individual applications and their interactions with the platform layer. This layer defines specific performance metrics and tuning parameters.

4. **Management Layer**  
   Integrates insights from both layers to make real-time adjustments based on performance metrics and resource availability. The management API is exposed over gRPC on port 4426/4427 ([ADR-011](docs/adr/adr-011-port-assignment.md)) and HTTP on port 8081, with access controlled by [ADR-015](docs/adr/adr-015-user-access-control-identity-provider.md).

## Agent Mapping
Agent mapping connects both OS-level and workload-level twins to create an interactive ecosystem. Each agent is an **agentic AI-capable agent**: it hosts an AI reasoning loop that autonomously observes, plans, and acts (see [ADR-007](docs/adr/adr-007-agentic-ai-agent-model.md), [ADR-008](docs/adr/adr-008-ai-model-selection.md)). The digital twin is a *skill* the reasoning loop invokes — agents read the twin model to understand desired state, compute the gap against actual state, and apply the model to the system under management without explicit command-response cycles. Reasoning traces and twin diffs are captured as structured observability events (see [ADR-019](docs/adr/adr-019-agent-ai-observability.md)). This mapping enhances visibility across the entire topology, allowing for streamlined, autonomous operations and responses.

## Observability
The platform provides a full observability stack: Prometheus metrics, Grafana dashboards, structured logs, and AI decision traces (see [ADR-018](docs/adr/adr-018-observability-stack.md) and [ADR-019](docs/adr/adr-019-agent-ai-observability.md)). The stack is deployable locally via Docker Compose — see the [README](README.md#local-development-with-docker) for quick-start instructions.

## Challenges
- **Scalability:** Managing a large number of twins can complicate monitoring and orchestration.
- **Data Overhead:** High data volume generated by multiple twins can lead to performance bottlenecks unless adequately managed (addressed by the hybrid in-memory + etcd architecture in [ADR-002](docs/adr/adr-002-server-architecture.md)).
- **Integration Complexity:** Integrating data across layers and ensuring consistency can be challenging, particularly with disparate systems.
- **Real-Time Processing:** Achieving real-time insights requires efficient data processing and communication frameworks.

## Conclusion
Using a 1:Many model for digital twins provides a robust solution for managing server topology and workloads by leveraging both OS-level and workload-level twins. The agentic AI loop, gRPC contracts, and hybrid persistence layer together provide the scalability, observability, and autonomy required for production-grade distributed infrastructure management.
